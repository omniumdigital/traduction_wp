## Étape 3 — Revue manuelle des points critiques

### 3.1 Réponses de l'IA = entrées non fiables — OK

Les slugs générés passent par `SlugGenerator::normalize()` (ASCII) puis `unique()` — jamais réinsérés en HTML sans échappement.

### 3.2 Contrôle d'accès — OK
Aucune route nouvelle ; les 22 routes REST conservent `permission_callback = Capabilities::rest_permission` (`current_user_can('omtr_manage')`, src/Admin/RestController.php:54). `put_key` (src/Admin/Administration.php:291) reste derrière la même permission. `Capabilities::ensure_granted()` (src/Security/Capabilities.php:44) n'accorde `omtr_manage` qu'au rôle **administrator** (via `get_role('administrator')`), une seule fois, et jamais si `omtr_caps_granted` est présent : un retrait volontaire n'est jamais contourné (testé : tests/Unit/CapabilitiesTest.php, tests/Unit/ActivatorTest.php — `@group security`).

### 3.3 Clés API — OK
`put_key` renvoie `{set, masked, provider, switched}` (src/Admin/Administration.php:315-322) : seul le masque `sk-…` de `ApiKeyStore::masked()` (src/Security/ApiKeyStore.php:54-57) part vers le navigateur — jamais la clé (test : tests/Unit/AdministrationSecurityTest.php::test_put_key_switches_active_provider_without_key vérifie que la clé absente de la réponse). La détection « fournisseur actif sans clé » utilise `masked()`, pas la clé. Aucune clé dans les logs : le garde journalise `provider "id"` uniquement (src/Queue/ActionSchedulerQueue.php:446, testé par test_enqueue_url_refused_when_active_provider_has_no_key).

### 3.4 Abus et coûts — OK (amélioré)
